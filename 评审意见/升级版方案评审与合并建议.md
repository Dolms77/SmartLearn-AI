## 2. 硬伤一：关键数字口径错误（会被现场问穿）

### 2.1 最严重：班级得分率张冠李戴

方案 4.1 仪表盘写：

```
DC01 ████████ 56.5%      DC02 ██████ 59.3%   (按主题分列)
```

实测（`得分和/满分和` 口径）：

| 口径 | DC01 | DC02 | 结论方向 |
|---|---|---|---|
| **班级总体** | **60.03%** | **55.44%** | DC01 > DC02（差 4.6 pt） |
| T01 | 56.53% | 59.34% | DC02 > DC01（差 2.8 pt） |
| T02 | 61.06% | 49.30% | DC01 > DC02（差 11.8 pt） |
| T03 | 65.82% | 57.66% | DC01 > DC02（差 8.2 pt） |

**56.5 / 59.3 是 T01 的两个数**，被当成了班级总体写进仪表盘。后果：
- 仪表盘与正文"DC02 在 T02 落后 DC01 约 12 个百分点"自相矛盾；
- 评委若现场复算总体分，会得到"DC01 更好"，与图上相反 → "统计准确性"直接失分。

## 3. 硬伤二：BKT 在本数据上不可辨识，输出会变成"伪精度"

### 3.1 证据密度不够（关键）

学生×指标共 **360 个单元格**（40 人 × 9 指标，已排除学习卡的多值指标）：

| 每单元格证据条数 | 0 | 1 | 2 | 3 | 4 | 5 | ≥6 |
|---|---|---|---|---|---|---|---|
| 单元格数 | **67** | 70 | 93 | 56 | 35 | 24 | 15 |
| 占比 | **18.6%** | 19.4% | 25.8% | 15.6% | 9.7% | 6.7% | 4.2% |

- **63.9% 的单元格只有 ≤2 条证据**，BKT 的 4 个参数完全无法逐生逐指标辨识；
- **18.6% 的单元格 0 条证据**，若用先验 `P(L0)=0.5`，模型会输出"掌握概率 50%"——这正是赛题明令禁止的"把缺少记录解释为已掌握/未掌握"；
- 例：D01 的 T03I3 是 0 条、T02I2 只有 1 条；而方案声称"D01 的 T03I1 掌握概率 0.25"（该单元格实际 4 条，勉强可算，但没有任何不确定性表达）。

### 3.2 参数固定 ⇒ BKT 只是得分率的单调变形

方案把 `P(L0)=0.5, P(T)=0.3, P(S)=0.1, P(G)=0.2` 全部写死。在这个设定下，每次答对掌握概率被推高、答错被压低，**最终输出完全是"答对次数"的单调函数**，并没有引入新信息；而 `P(T)=0.3`（每次练习提升 30%）会让 3–4 次作答后掌握概率饱和到 0.9+，所谓"0.32 vs 0.25"的区分度是假的。

更专业的表述应该是"**加权掌握度 + 证据量 + 置信区间**"。若确要保留概率外衣，至少要：
1. 参数用**全样本 EM 估计**而非手设；
2. 只有证据数 ≥3 才输出概率，否则输出 `insufficient`；
3. 输出区间（如 Wilson 下界）而非点估计。

### 3.3 二值化丢掉了最有价值的信息

解答题有 3 个评分点、260 条记录，其中大量是 1/3、2/3 的**部分得分**。BKT 只吃"对/错"，等于把"会做但没写检验"和"完全不会"合并成同一类——而这恰好是本题最想区分的。→ 建议改用**按得分率加权的掌握度**（`Σ得分/Σ满分`）或 IRT 的部分给分模型（GPCM），并在结论里保留评分点画像。

### 3.4 "级联错误"结论建立在 n=9 上

`Q043P2=0%` 与 `Q043P3=0%` 属实，但 **Q043 只有 9 名学生作答**（40 人中 22.5%）。"全班 0%"的正确表述是"**在 9 名作答者中 0 人正确，样本占全班 22.5%，不足以代表全班**"。方案把它写成"全班共性难点"，属于典型的以偏概全，且与赛题"避免过度解读"的口径冲突。

## 4. 硬伤三：代码级 bug（若原样运行必报错）

```python
class SimpleBKT:
    def __init__(self, indicator_id):
        self.p_L0, self.p_T, self.p_S, self.p_G = 0.5, 0.3, 0.1, 0.2
        # ❌ 没有 self.current_mastery

    def update(self, is_correct):
        p_L = self.current_mastery        # ❌ AttributeError
        if is_correct:
            p_L_given = (p_L * (1 - self.p_S)) / (...)      # ✅
        else:
            p_L_given = (p_L * self.p_S) / \
                (p_L * self.p_S) + (1 - p_L) * (1 - self.p_G)   # ❌ 缺括号，
                # 实际等于 1 + (1-p_L)(1-p_G)，恒 >1
```

三处必须修：
1. `__init__` 缺 `self.current_mastery = self.p_L0`；
2. 答错分支分母缺一对括号（运算优先级错误，结果恒 >1）；
3. **符号命名与公式不一致**：文中定义 `P(S)=猜对概率`、`P(G)=失误概率`，但标准 BKT 是 `slip`（会而错）与 `guess`（不会而对），且答对分支用 `(1-slip)`、答错分支用 `slip`。按标准，方案里的 `P(S)` 实际扮演 slip、`P(G)` 扮演 guess，与自己的定义相反。评委只要懂 BKT 就会追问。

## 5. 硬伤四：与"自训练开源模型"的目标不一致（本队最关键的问题）

方案全篇是 **DeepSeek API + LangChain**，没有任何训练环节：

| 维度 | 升级版方案 | 你的目标 | 冲突后果 |
|---|---|---|---|
| 模型 | DeepSeek-V3/Chat API | 自训练开源模型 | 答辩讲"自行训练"时无法自证 |
| 数据 | 学情数据发往第三方 API | 赛事数据"不得外传" | 合规风险，需在文档中说明并最好本地化 |
| 演示 | 依赖现场网络 | 现场网络不可控 | 断网即演示失败 |
| 成本/复现 | 依赖 API key 与额度 | 需可复现 | 评委无法复跑 |

**建议**：本地 **Qwen2.5-7B-Instruct + QLoRA + GGUF/Ollama** 作为主链路（8 GB 显存可跑，见《技术方案与实施指引》），API 仅作离线训练时的"数据合成教师"，并在文档里明确写"教师模型仅用于构造训练数据，推理全程本地"。这样既满足"自训练"，又满足"数据不外传"，还能断网演示——三个加分点一次拿满。

另有两处技术性错误：
- **"DeepSeek Embedding" 不存在**：DeepSeek 开放平台目前没有 embedding 接口，2.1.2 里"使用 DeepSeek 或 BAAI/bge-small-zh"只有后者可行。建议统一 `BAAI/bge-m3`（中文更强，CPU 可跑）。
- **`Chroma + langchain_community` 在 Windows 上是高危依赖**（chromadb 版本与 pydantic 冲突频发）；本任务语料仅约 1000 块，用 `faiss-cpu + sqlite` 或纯 `numpy` 余弦检索即可，稳定性高一个量级。

## 6. 硬伤五：RAG 没有页码元数据 → 拿不到"材料依据"分

方案 2.1.3 让 AI 回答"对应课标 CR03（第 63/56 页）、教材第 120–145 页"。但 2.1.2 的实现只有 `RecursiveCharacterTextSplitter`，**chunk 里没有任何页码/章节元数据**，这段页码只能来自 LLM 记忆 —— 即幻觉。

正确做法（我已实测标定）：
- 课标：`PDF 页 = 正文页 + 7`（PDF p62 = 正文 p55）；
- 教材：`B05 PDF 页 = 印刷页 − 67`（p1 = 印刷 p68，42 页）；
- 每个 chunk 携带 `{file, pdf_page, print_page, chapter, section, topic, indicator}`，回答时以 `[B05 p12]` 形式回填并做白名单校验。

**这是 80% 资料评审中最容易被扣分、也最容易补上的一项。**

## 8. 工程与组织风险

| 风险 | 说明 | 建议 |
|---|---|---|
| 4-Agent 过度设计 | 任务是固定的三条流水线，Coordinator 路由没有增益；多一层 LLM 调用就多一处不确定性、多 2–5 秒延迟 | 保留"Agent"叙事（答辩话术），实现用**固定编排 + 3 个工具函数**，只在一个入口用 function-calling |

## 9. 合并建议：最终架构（保留 ×4，替换 ×4，新增 ×5）

### 9.1 保留
1. **错因体系 C1–C6**（改称"评分点模式→错因映射"，给可验证定义，去掉"独创"表述）；
2. **全链路溯源**（每条结论强制 `record_ids`）；
3. **知识图谱 + 4 张核心图**；
4. **RAG 问答入口**（补页码元数据后）。

### 9.2 替换
| 原方案 | 替换为 | 理由 |
|---|---|---|
| BKT（固定参数） | **证据加权掌握度 + 证据量 + Wilson 区间**，≥3 条才出等级 | 数据不支持 4 参数辨识；满足"信息不足"要求 |
| DeepSeek API 主链路 | **本地 Qwen2.5-7B LoRA（自训练）+ GGUF 部署**，API 只做数据合成 | 自训练目标 + 合规 + 断网演示 |
| LangGraph 4-Agent | **固定编排 + 工具函数 + 单一 function-calling 入口** | 稳定、可复现、延迟低 |
| Chroma + langchain embedding | **faiss-cpu + bge-m3 + 自写 chunker** | 依赖少、页码可控 |
| （缺失） | **新增：清洗规则引擎 + 清洗日志表** | 补"数据处理"评分项 |

### 9.3 新增（当前最大缺口）
1. `config/clean_rules.yaml` 8 条规则 + 命中记录表（数据里已定位 8 类异常）；
2. 证据量门槛与 `insufficient` 等级；
3. **模拟独立评测集**：按学生留出（D37–D40）+ 删 30% 记录 + 注入待评分/越界分；
4. **20 页 PDF 结构 + 5 分钟视频分镜**（见实施指引第 8 节）；
5. **JSON Schema ×3 + 输入输出样例**（提交物②"附字段说明、输入输出样例"是硬性要求）。

### 9.4 合并后的五层架构

```
展示层：Gradio 三 Tab + 知识图谱 + 4 图看板 + 一键导出
编排层：clean → aggregate → retrieve → generate → validate → persist（固定 DAG）
智能层：本地 Qwen2.5-7B(LoRA) ｜ bge-m3+faiss ｜ 规则引擎 ｜ 加权掌握度
数据层：DuckDB（6 原表 + clean_log / evidence_index / mastery）
输出层：task1/2/3 JSON + CSV + 证据链 Markdown + schema
```

## 12. 一句话总结

> 升级版的**展示层**值得直接抄（错因体系、溯源、图谱、可视化），但**证据层**（清洗、页码、证据量、不确定性、泛化）几乎空白，且有一个会被现场问穿的班级数字错误。**正确做法是：用它的壳，装我们已验证的芯**——本地 LoRA 生成 + 规则引擎统计 + 带页码的 RAG，三项任务产物全部挂 `record_ids`。
